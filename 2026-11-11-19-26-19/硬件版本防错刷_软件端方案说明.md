# 关于 H.1 / H.2 硬件版本与 V001 / V002 软件版本防错刷的软件端方案说明

## 一、结论先行

针对"V002 被误刷入 H.1"的问题，软件端的核心手段不是加密，而是**身份识别 + 升级前校验**。

- **加密**解决的是"固件被提取、被逆向"，属于知识产权保护，会引入密钥管理、产线烧录、售后维护的额外成本；
- **校验**解决的是"合法固件装错了设备"，正是本问题的成因。

误刷场景下，固件本身是合法的、完整的，只是"装错了板子"。因此需要的是让软件在升级前能确认"我该不该装在这块板子上"，而不是把固件藏起来。结论：**版本匹配校验 + 完整性校验必须做；数字签名和加密按需选配。**

## 二、四层防护，从源头到设备

| 层级 | 拦截时机 | 作用 |
| --- | --- | --- |
| 第一层：编译打包 | 固件生成时 | 从源头杜绝错误组合流出 |
| 第二层：升级工具 | 下发数据前 | 给用户明确提示，避免无效传输 |
| 第三层：Bootloader | 收到文件头、擦写 Flash 前 | **强制拦截，不可绕过** |
| 第四层：运行自检 | 软件启动时 | 兜底，便于产线定位问题 |

**第一层 · 编译打包（源头拦截）**
固件编译完成后，由脚本自动在文件头部写入软件版本号、支持的硬件版本、镜像长度和校验值，并与版本对照表比对。若出现"V002 声明支持 H.1"这类错误组合，构建直接失败，错误升级包根本不会产生。这是成本最低的一层。

**第二层 · 升级工具（体验拦截）**
工具先向设备查询当前硬件版本，再解析升级包的支持列表。不匹配则弹窗提示并终止，一个字节都不下发，避免用户等待数分钟后才失败。

**第三层 · Bootloader（强制拦截）**
这是唯一不可绕过的防线。即使有人用串口工具或调试器直接灌包，Bootloader 在收到 64 字节文件头后，会依次校验：固件标识 → 头部长度 → 头部校验值 → 本机硬件版本比对 → 镜像长度 → 镜像校验值。任何一项不通过立即丢弃数据包并退出升级模式，原有固件照常运行。全部通过才允许擦写 Flash。

**第四层 · 运行自检（兜底）**
软件启动时再读一次硬件版本，与本版本编译时声明的目标硬件比对。不一致则进入安全模式并上报故障码，便于产线和售后快速定位，而不是表现为"莫名其妙的功能异常"。

## 三、固件包格式

每个升级包 = 64 字节固定文件头 + 应用镜像。

| 字段 | 作用 |
| --- | --- |
| 固件标识（魔数） | 识别是否为合法升级包 |
| 头部版本 / 长度 | 预留后续扩展，同时用于边界校验 |
| 软件版本号 | V001 / V002，采用数值编码便于判断升降级 |
| 支持的硬件版本 | **位掩码**，可声明支持单个或多个硬件 |
| 镜像长度 | 用于边界校验，防止越界读取 |
| 镜像校验值 | CRC32，校验传输完整性与写入正确性 |
| 头部校验值 | CRC32，防止版本字段被误改 |
| 预留区 | 签名摘要、防回滚计数等后续扩展 |

两个设计要点：

1. **硬件版本用位掩码，不用单一数值。** 将来若出现 H.1 / H.2 通用的固件（例如只换物料、不改软件），一个包可同时声明支持两个版本，无需拆包。
2. **头部校验值与镜像校验值分开计算。** 头部校验只覆盖头部，镜像校验只覆盖镜像。这样 Bootloader 收完 64 字节即可判断"该不该继续收"，而不必等整个包传完——这正是"错误包根本不进入 Flash"的前提。

## 四、硬件版本如何识别

| 方式 | 说明 | 成本 | 适用 |
| --- | --- | --- | --- |
| GPIO 上下拉 / ADC 分压 | 改板时预留 2~3 个引脚，H.1 下拉、H.2 上拉；或用不同阻值分压读 ADC | 零器件成本 | **推荐首选** |
| OTP / eFuse | 芯片出厂烧录阶段写入版本号，不可更改 | 需产线烧录工位 | 防篡改要求高 |
| 板载 EEPROM / Flash 标志位 | 产线测试时写入 | 增加器件与工位 | 需频繁变更版本 |

**硬性要求：Bootloader 必须能独立读取硬件版本**，不能调用应用层代码——否则应用一旦损坏，校验就失效了。

## 五、加密与校验的定位

| 手段 | 解决的问题 | 本场景是否必须 |
| --- | --- | --- |
| 版本匹配校验 | 固件装错硬件 | **必须** |
| CRC / 哈希校验 | 传输丢包、Flash 写入损坏 | **必须** |
| 数字签名（如 ECDSA） | 防止他人篡改版本字段绕过校验、阻止非官方固件 | 按需 |
| 固件加密（AES） | 防止固件被提取、逆向分析 | 按需 |

判断标准：若产品面向公开市场、担心第三方改包绕过校验，建议引入签名；若为自有产线、售后体系可控，**CRC + 版本校验已完全足够**，性价比最高。

## 六、实施建议（分三期）

**第一期 · 必做（改动最小，即可解决误刷）**
固件头格式定义 + 打包脚本 + Bootloader 版本校验 + 升级工具端预检。

**第二期 · 建议（提升可靠性）**
运行自检与故障码上报 + 升级失败回滚（备份区或 A/B 双区）+ 断电保护。

**第三期 · 按需（安全增强）**
数字签名、防降级计数。

## 七、需要贵方确认的四点

1. H.1 / H.2 是否已预留硬件版本识别引脚？若无，是否接受改板，或改用 OTP 方案？
2. 现有 Flash 是否支持双区（A/B）或预留备份区？这决定断电保护能做到什么程度。
3. 是否需要防降级（禁止刷回旧版本）？涉及单调计数器，需要 OTP 支持。
4. 是否有防固件提取、防第三方改包的需求？这决定是否引入签名与加密。

## 八、验收要点

| 测试项 | 期望结果 |
| --- | --- |
| V002 包刷 H.1（正常流程） | 工具端弹窗拦截，不传输 |
| V002 包刷 H.1（绕过工具，直连串口） | Bootloader 拒绝，旧固件仍可启动 |
| V001 包刷 H.2（反向验证） | 同样拦截 |
| 篡改包内硬件版本字段 | 头部校验失败，拒绝升级 |
| 传输中途断电 | 重启后旧固件正常运行 |
| 硬件版本引脚悬空 / 读取异常 | 判为未知硬件，拒绝升级而非放行 |
