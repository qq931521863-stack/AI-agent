# DSP 固件升级模块设计方案

> 范围说明：本方案只覆盖 **DSP 固件升级链路**（升级通道 + Bootloader + Flash 管理 + 校验回滚）。
> 不涉及算法移植、硬件改版、上位机业务功能。目标是"升得进去、升得对、升坏了能回来"。

---

## 0. 一句话定义这个模块

> 把一份带版本号和校验的固件镜像，从外部（上位机 / 主控 MCU / 网络）可靠地写进 DSP 的 Flash，
> 保证在任何时刻断电都不会让设备变成砖，并在升级后能自动确认或自动回滚。

如果这句话里任何一个环节没做到，模块就不算完成。

---

## 1. 开工前必须钉死的 8 个参数

这 8 项决定架构，**定不下来就不要写代码**，否则大概率返工。

| # | 参数 | 影响 |
|---|---|---|
| 1 | 固件体积（KB）与增长预期 | 分区大小、升级耗时、是否需压缩 |
| 2 | 升级通道（UART / CAN / SPI / 以太网 / USB） | 协议设计、吞吐、是否需要流控 |
| 3 | 谁发起、谁搬运 | 决定是 DSP 自举升级，还是外部主控代烧 |
| 4 | 可接受的升级时长 | 决定分包大小与是否压缩、是否必须在线升级 |
| 5 | 是否允许停机升级 | 决定要不要 A/B 双区 |
| 6 | Flash 容量与扇区（擦除）粒度 | 分区对齐、擦除策略、参数区保护 |
| 7 | 掉电/中断的容错等级 | 决定是否有回滚、几级备份 |
| 8 | 是否需要降级（回退到旧版本） | 决定版本校验策略与镜像保留策略 |

**第 3 项是最容易被忽略的分叉点**：很多 DSP 方案里，DSP 从挂在外部主控（MCU/FPGA）总线上的 SPI Flash 启动，
此时 DSP 运行时并不能直接访问这块 Flash，升级必须由主控完成，DSP 只是被动重启。
这种情况下你要做的是**主控侧的烧写时序 + DSP 侧的重启握手**，而不是 DSP 内部的 Bootloader。先确认这一点。

## 2. 总体架构：三段式

```
[ 上位机 / 产线工具 ]  --(升级协议)-->  [ 传输与协议层 ]  -->  [ Bootloader + Flash 管理 ]
        固件包                          帧解析/重传/续传           分区/擦写/校验/跳转
```

三层职责必须严格分开，任何一层都不做别人的事：

- **上位机侧**：组包、进度显示、失败原因码解释、日志留存。不关心 Flash 怎么擦。
- **协议层**：只负责"把一段字节完整、有序、可重传地送达"。不关心这段字节是代码还是参数。
- **Bootloader 侧**：只负责"把收到的字节写进正确的地址并保证可启动"。不关心数据从哪来。

这样分层的好处是：换通道（UART 换 CAN）只动协议层，换芯片只动 Bootloader 侧。

## 3. Flash 分区规划

### 3.1 推荐布局（A/B 双区 + 独立元数据）

| 区域 | 内容 | 是否可擦 | 说明 |
|---|---|---|---|
| Boot | Bootloader 代码 | 仅专用流程 | 最小化，只依赖芯片 ROM 与内部 RAM |
| Meta | 启动标志、当前版本、镜像 CRC、启动失败计数、A/B 指针 | 可（需双备份） | **整个方案的"真相源"**，必须做两份互为备份 |
| Image A | 应用镜像 A | 可 | |
| Image B | 应用镜像 B | 可 | 与 A 等大 |
| Params | 标定参数、序列号、校准系数 | 升级时**禁止**擦除 | 单独扇区，物理隔离 |

### 3.2 三条硬规则

1. **Bootloader 永不参与常规升级**。它一旦损坏，设备只能返厂。若必须支持 Bootloader 自升级，用两级结构：
   ROM 引导 → 常驻 Mini-Boot（不可升级）→ 可升级的主 Bootloader。
2. **Meta 区双备份 + 序号**。写 Meta 时先写备份区，再写主区，读取时取序号大且 CRC 正确的那份。单份 Meta 是变砖的头号原因。
3. **擦除粒度对齐**。分区起始地址必须落在扇区边界上；分包大小必须是写入对齐单位的整数倍（很多 DSP Flash 要求 8/16 字节对齐写入）。

### 3.3 容量估算

```
所需 Flash = Boot + 2 × Meta + 2 × Image + Params + 10% 余量
```
不要按"刚好装下"来算。固件一定会变大，留 10%~20% 余量比事后改分区便宜得多。

## 4. 启动决策与回滚

上电后的判断顺序（顺序错了就会变砖）：

1. 初始化时钟、看门狗、最小 RAM。
2. 读 Meta 主/备两份，选出有效的那份（CRC 正确 + 序号最大）。
3. 若无有效 Meta → 进入升级等待模式（**不是死机**，要能通过通道被救回来）。
4. 按 Meta 指针定位活动镜像，校验**整包 CRC**（不是只看标志位）。
5. 校验通过 → 跳转；校验失败 → 尝试另一区。
6. 跳转前把"启动尝试计数 +1"写入 Meta；应用启动成功后，由应用在 N 秒内**回写"启动成功"标志**并清零计数。
7. 若计数超过阈值（如 3 次）仍未见"启动成功" → 自动回滚到另一区，并置回滚标志供上位机读取。

**关键点：第 6 步的"应用确认"是整个回滚机制的核心。** 没有它，你只能判断"镜像 CRC 对不对"，判断不了"这个固件跑起来是不是死循环"。

### 4.1 提交的原子性

写镜像的过程可以随时中断（重来即可），但**"提交"必须是一次原子写**：

```
写目标镜像区 → 读回校验 CRC → 写 Meta 新记录（指向新镜像 + 版本号）
```
只有 Meta 写成功，升级才算生效。在此之前断电，设备仍然启动旧镜像 —— 这就是"永不砖"的本质。

## 5. 升级协议设计

### 5.1 帧格式（示例）

| 字段 | 长度 | 说明 |
|---|---|---|
| 帧头 | 2B | 固定魔数，如 0xA5 0x5A |
| 命令 | 1B | 见命令集 |
| 序号 | 2B | 用于重传与去重 |
| 长度 | 2B | 载荷字节数 |
| 载荷 | N | 数据 / 参数 |
| CRC16 | 2B | 覆盖命令到载荷 |

### 5.2 命令集（最小可用集）

| 命令 | 作用 | 备注 |
|---|---|---|
| HANDSHAKE | 进入升级模式、协商版本与分包大小 | 带超时，失败回正常启动 |
| GET_INFO | 读取芯片型号、当前版本、Flash 布局 | 升级前必做兼容性检查 |
| ERASE | 擦除目标区（可分段） | 耗时最长，需延长超时 |
| WRITE | 写一包数据 | 带偏移地址，天然支持续传 |
| VERIFY | 读回校验（整包或分段） | 不只依赖传输层 CRC |
| COMMIT | 提交：写 Meta、切换指针 | 唯一的"生效"动作 |
| REBOOT | 复位并进入新固件 | |
| ABORT | 中止并清理 | 保留旧镜像 |

### 5.3 可靠性机制

- **超时重传**：每包等待 ACK，超时 N 次则重发，连续失败则中止（保留现场）。
- **断点续传**：WRITE 带绝对偏移，重连后从 Meta 或查询命令得到已写偏移，从断点继续。
- **流控**：分包大小与 Flash 页大小对齐；不要为了"快"用超大包，重传代价会吃掉收益。
- **顺序保证**：Bootloader 拒绝非连续偏移的写入（防错位）。

### 5.4 耗时预算

有效吞吐 ≈ 链路速率 × 0.7（协议开销 + 擦除等待 + 重传）。

| 通道 | 典型有效吞吐 | 256KB 固件耗时 |
|---|---|---|
| UART 115200 | ~10 KB/s | 25~35 s |
| CAN 500k | ~35 KB/s | 8~12 s |
| 以太网 100M | ~2 MB/s | < 1 s（瓶颈在 Flash 擦写） |

> 注意：以太网场景下瓶颈通常不是网络，而是 **Flash 擦除时间**。擦一个扇区几十毫秒，几百个扇区就是十几秒，这部分无法通过提速通信解决。

## 6. DSP 特有的擦写约束（最容易出事的地方）

1. **不能在 Flash 中执行擦写 Flash 的代码**。
   擦写期间 Flash 无法取指，必须把擦写函数（含其调用的所有子函数、常量表、甚至中断向量）搬到 RAM 中执行。
   TI C2000 的 FlashAPI 就是这个套路：`MemCopy` 到 RAM 再调用。这是新手第一大坑。
2. **中断向量必须重定位**。DSP 常把向量表放 Flash 起始处，擦除时会一起没了。要么重定位到 RAM，要么在擦写期间全程关中断并保证无中断触发。
3. **擦写期间喂狗**。整片擦除可能几百毫秒到数秒，看门狗会先把你复位。擦除循环里要插喂狗，或临时放宽看门狗。
4. **写保护/安全区**。部分 DSP 有 CSM/安全区、扇区写保护位，升级前要确认目标区可写，否则表现为"写成功但读回全 FF"。
5. **ECC / 坏块**。带 ECC 的 Flash 写入未擦除区域会报 ECC 错误，务必"先擦后写"，不要假设可以覆盖写。
6. **代码重定位**。多数 DSP 是"Flash 启动 → 拷到 RAM 运行"，所以升级后**必须复位重启才生效**，不能指望热切换。设计上要把"升级完成 → 提示重启 → 重启后确认"做成显式流程。

## 7. 状态机（模块的骨架）

```
IDLE ──握手──> HANDSHAKE ──检查通过──> PREPARE(擦除) ──> TRANSFER ──> VERIFY ──> COMMIT ──> REBOOT ──> CONFIRM
  ^                  │                      │              │            │          │
  └──── 超时/中止 ────┴──────────────────────┴──────────────┘          │          │
                                                                        └─失败─> 回滚到旧区
```

| 状态 | 进入条件 | 超时 | 异常出口 |
|---|---|---|---|
| IDLE | 上电 / 升级结束 | — | — |
| HANDSHAKE | 收到握手帧 | 3 s | 回 IDLE，正常启动 |
| PREPARE | 兼容性检查通过 | 30 s | 回 IDLE，不破坏旧镜像 |
| TRANSFER | 擦除完成 | 每包 1 s | 保留已写偏移，可续传 |
| VERIFY | 收齐全部数据 | 10 s | 回 TRANSFER 重传指定段 |
| COMMIT | 校验通过 | 5 s | 保持旧 Meta，等同未升级 |
| REBOOT | 提交成功 | — | 启动失败计数 +1 |
| CONFIRM | 应用上报成功 | 应用侧 N s | 计数超阈值 → 自动回滚 |

**每个状态都要有明确的超时和异常出口**，不允许出现"卡在某处等"的状态。这是评审时最该逐条过的表。

## 8. 固件包格式

```
[ 包头 32B ]
  magic(4) | 格式版本(2) | 目标芯片ID(4) | 硬件版本(2)
  固件版本(4) | 载荷长度(4) | 载荷CRC32(4) | 包头CRC16(2) | 保留
[ 载荷：应用镜像 ]
[ 包尾：整体 CRC32 ]
```

- **目标芯片 ID 与硬件版本必须校验**，防止把 A 板固件刷进 B 板。
- 版本号要能比较大小，支持"禁止降级"策略（安全需求下常见）。
- 包尾 CRC 与包头 CRC 分开：包头坏了要能立刻拒绝，不用传完 256KB 才发现。

## 9. 异常与恢复矩阵（评审必看）

| 异常 | 发生时机 | 期望行为 |
|---|---|---|
| 断电 | 擦除中 | 旧镜像完好，重启后正常启动旧版本 |
| 断电 | 传输中 | 同上；Meta 未变，等同未升级 |
| 断电 | 写 Meta 中 | 双备份生效，读到旧记录，启动旧镜像 |
| 断电 | 重启瞬间 | 启动计数已 +1，若反复则回滚 |
| 通信中断 | 传输中 | 超时退出，保留偏移，重连续传 |
| 镜像错误 | VERIFY | 拒绝提交，旧镜像不受影响 |
| 芯片不匹配 | HANDSHAKE | 立即拒绝，不擦除任何区域 |
| 新固件死机 | 首次运行 | 应用未回写确认 → 计数达阈值 → 自动回滚 |
| Bootloader 损坏 | — | 只能返厂；用 Mini-Boot 规避 |
| Flash 写失败 | WRITE | 报错码 + 不提交，可重试 |

## 10. 测试用例清单（至少覆盖这些）

**正常路径**
1. 正常升级全流程，版本号正确更新
2. 同版本重复升级（幂等）
3. A→B→A 来回切换各 5 次

**掉电/中断**（用可编程电源做，这是最值钱的一组）
4. 擦除 10% / 50% / 90% 时断电
5. 传输 50% 时断电
6. 写 Meta 主区后、备份区前断电
7. COMMIT 后、REBOOT 前断电
8. 升级中拔通信线，再重连续传

**异常输入**
9. 错误芯片 ID 的固件包
10. CRC 被篡改的固件包
11. 截断的固件包（长度不足）
12. 超长固件包（超出分区）
13. 乱序/重复帧、错误序号
14. 波特率/链路质量差导致的高丢包

**边界**
15. Flash 写满、分区边界写入
16. 参数区在升级后是否完好（逐字节比对）
17. 升级期间看门狗是否误复位
18. 连续升级 100 次后的 Flash 寿命与稳定性

## 12. 常见坑速查

- ❌ 擦写函数留在 Flash 里执行 → 擦除瞬间取指失败死机
- ❌ 先写"升级成功"标志再写镜像 → 掉电即砖
- ❌ Meta 只存一份 → 写坏就砖
- ❌ 只做传输层 CRC，不做镜像整包 CRC → 传对了但写错了查不出来
- ❌ 擦除范围覆盖参数区 → 标定值全丢
- ❌ 长擦除不喂狗 → 反复复位，升级永远不成功
- ❌ 中断向量在 Flash 未重定位 → 擦除时异常
- ❌ 没有"应用启动确认"机制 → 新固件死循环无法自动回滚
- ❌ 升级后想热切换不重启 → DSP 代码在 RAM 中运行，改了 Flash 不生效
- ❌ 没有版本比较 → 无法阻止降级到有漏洞的旧版本

## 附：需要你确认的三件事

1. **谁执行烧写**：DSP 自己从 Flash 自举并自升级，还是外部主控代烧？
2. **升级通道与速率**：UART / CAN / SPI / 以太网？决定协议复杂度与耗时预算。
3. **现有 Bootloader 是否存在**：从零做，还是在已有 ROM boot + 二级 boot 上改？
